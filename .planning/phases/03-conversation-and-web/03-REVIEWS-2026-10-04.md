## 03-01

### Summary
The plan identifies the right critical gates: encrypted whole-state capacity, atomicity, plaintext absence, one-active-turn semantics, and canonical idempotency. The main acceptance is not checkpoint-safe yet: its formal task completion criteria and verification command omit two mandatory architecture-gate outcomes.

### Strengths
- Reuses the existing encrypted store and limits the migration decision to whole-authority state rather than a second authority store (`.planning/phases/03-conversation-and-web/03-01-PLAN.md:70`).
- The reducer contract requires atomic message/receipt/dispatch-intent commit, duplicate-key rejection on changed payload, and retention while the turn is uncertain (`.planning/phases/03-conversation-and-web/03-01-PLAN.md:78-80`; `.planning/CONTRACT-CATALOG.md:79`).
- Current storage code actually reads and rewrites one complete snapshot under the Store mutex (`internal/store/store.go:238-270`), caps the envelope at 8 MiB (`internal/store/store.go:286-293`), and uses injected filesystem hooks in atomic commit (`internal/store/store.go:322-395`). This makes the proposed E4 a real risk-reduction gate.

### Concerns
- **HIGH — E4 can be marked complete without passing the decision gate.** Task 1's `<done>` requires only crash-recovery outcomes and no plaintext (`03-01-PLAN.md:69-72`); its `<verify>` runs ordinary store tests only (`:71`). Neither requires workload size under the 8 MiB limit nor p95 acceptance below 100 ms, although the action makes both hard gates (`:70`). The following conversation implementation task is in the same plan (`:74-81`), so an executor can proceed after Task 1 is marked done with an oversized/unreadable workload or failed latency gate. Make measured E4 outcomes explicit in must-haves and Task 1 done; add a BLOCKED checkpoint that stops Tasks 2 and all downstream phase plans until a separately reviewed whole-authority decision is approved. The underlying cap is concrete in `internal/store/store.go:286-291`; the target workload/metric is in `docs/PLAN.md:348-358` and experiment E4 in `:367`.
- **MEDIUM — E4 has no reproducible workload/benchmark artifact or command.** The task says “run E4” and record results but owns only store implementation/tests/evidence (`03-01-PLAN.md:7-15,65-72`); verification is `go test ./internal/store -count=1`, which does not run a benchmark (`:71`). `docs/PLAN.md:356-367` requires declared hardware, payload/concurrency, crash injection, and an existing-store-versus-candidate decision. Specify a named fixture generator or benchmark/test harness, exact measured operation boundary (Host acceptance vs Store.Update), warm-up/sample count/percentile method, fault injection matrix, and an exact command/output schema in the plan. Otherwise a basic executor must invent the gate measurement and may report incomparable p95 values.

### Suggestions
- Add a durable E4 decision/evidence schema and explicit pass/fail/blocked fields for encoded bytes, encrypted bytes, peak memory/write size, p95, atomicity cases, and plaintext scan; identify who approves a migration plan before execution.
- Reuse existing reducer and store behavior wherever it already satisfies the contract; keep the fixture compatibility decision and migration gate explicit.

### Risk Assessment
**HIGH.** A false pass at the storage gate can let the implementation proceed on a state size or latency profile that cannot be read or accepted.

## 03-02

### Summary
The plan has good durable-run invariants and explicitly forbids blind redispatch. It needs to align its “reuse preserved work” instructions and test ownership with the actual merged source tree.

### Strengths
- Requires certified runtime dispatch, immutable profile/context binding, stable Space identity, and durable run states (`03-02-PLAN.md:63-69`).
- Restart behavior explicitly retains an uncertain outcome when Hermes lookup is unavailable, and asks for Host/Hermes restart coverage (`:71-78`); this matches FR-30 (`.planning/REQUIREMENTS.md:31`) and the no-blind-retry contract (`.planning/CONTRACT-CATALOG.md:81`).

### Concerns
- **MEDIUM — reuse instructions still point an executor at a preserved branch/revision instead of the current merged implementation.** Task 1 says to review the “preserved continuity work revision and unresolved findings” before selective reuse (`03-02-PLAN.md:67`), while the target main already has `internal/conversation/service.go`'s accepted-intent, runtime certification, projection and durable dispatch path (`internal/conversation/service.go:127-220`), Host startup recovery (`internal/host/execution.go:430-458`), and conversation-specific recovery separation (`:840-848`). This makes branch provenance an ambiguous prerequisite and invites duplicate implementations or stale-branch cherry-picks. Rewrite the step to first inspect current main and identify exact contract gaps; treat preserved-branch history/review only as provenance evidence, never as code to import absent a demonstrated missing change.
- **MEDIUM — task-level test commands omit the conversation package that owns the implementation.** Task 1 changes `internal/conversation/{service,projection}.go` (`03-02-PLAN.md:7-14,65`) but verifies only `go test ./internal/host` (`:68`). Include `./internal/conversation` in each focused verify and list/update its regression-test file as task-owned when implementation requires it. Broad `<verification>` text at `:94-95` is not a substitute for the task checkpoint command.

### Suggestions

## 03-03

### Summary
The authentication and replay design is unusually concrete and correctly treats Tailscale identity headers as hints. The plan does not yet complete the production path to a usable browser because static asset serving/packaging is absent, and HTTP resource bounds need explicit acceptance.

### Strengths
- Specifies loopback-only listener, private Serve (no Funnel), one-use owner-issued exchange, digest-only session storage, CSRF/origin checks, revocation, and a real HTTPS evidence gate (`03-03-PLAN.md:89-95`; `.planning/CONTRACT-CATALOG.md:83`).
- Defines snapshot watermark, replay registration order, gap/overflow behavior and race/restart tests (`03-03-PLAN.md:97-104`; `.planning/CONTRACT-CATALOG.md:85`).
- Files explicitly include owner-control operations and durable session reducers rather than placing the operator credential in browser code (`03-03-PLAN.md:18-24,91-94`).

### Concerns
- **HIGH — production UI assets are never served by the Host.** Canonical technology choice is “React + TypeScript, static build served by Host” (`docs/PLAN.md:266`). Plan 03-03 owns API/listener and Tailscale script but no static handler, embedded/build asset directory, or route fallback (`03-03-PLAN.md:7-24,89-104`); Plan 03-04 only runs `npm build` and tests source (`03-04-PLAN.md:7-11,53-69`). Current `internal/host/service.go:512-539` starts only the Unix control server. Thus even if API and UI build succeed, no planned step makes the browser UI available at the private HTTPS origin. Add the Host static-file serving/embedding/packaging files and tests, define how build output is generated and included in release artifacts, and test that the exact Tailscale origin serves the UI plus API with safe fallback and content security policy. Do not add a second listener outside the loopback contract.
- **MEDIUM — HTTP denial-of-service/slow-client bounds are not executable acceptance criteria.** The action says bound method/body/schema/scope and per-actor rate in the catalog (`03-03-PLAN.md:93`; `.planning/CONTRACT-CATALOG.md:83`) but neither plan pins max body/response bytes, header/read/write/idle timeouts, SSE subscriber/queue limits, or cancellation/cleanup when a client disconnects. The “slow-subscriber overflow” case is named (`03-03-PLAN.md:102`) without queue size, threshold, or expected persisted cursor result. Specify constants/config source and tests for slow headers/body, oversized responses, stalled SSE client, overflow, rate window, and stream cleanup; derive values in the contract before coding.

### Suggestions
- Freeze the route/request/response/error fixture with concrete examples for session exchange, conversation snapshot/send/status/stop, event replay and cursor resync; include auth, cookie, origin, CSRF and idempotency headers.
- Put exact executable security headers, server timeouts, body ceilings and per-client stream caps in the plan/contract; verify headers at the actual served origin.

### Risk Assessment
**HIGH.** The missing Host static-serving path leaves the central browser feature unreachable even after the planned API and React app are complete.

## 03-04

### Summary
The browser states and accessibility scope are a good start, but browser delivery and request recovery remain under-specified relative to the Host-owned authentication/replay contracts.

### Strengths
- Requires stable conversation IDs, committed/provisional distinction, duplicate suppression, reconnect snapshot/replay, truthful uncertain state, keyboard/accessibility checks (`03-04-PLAN.md:58,65-69`).
- React/TypeScript is a confirmed project technology choice (`docs/PLAN.md:266`), so the framework is not an unresolved assumption.

### Concerns
- **MEDIUM — “store pending request ID locally” has no privacy/lifecycle contract.** The plan does not name memory/sessionStorage/IndexedDB, removal conditions on receipt/revocation/logout, or whether storage may contain only opaque command IDs. Contract forbids putting operator credential, exchange code or Hermes credential in JavaScript storage and binds the session to a Host-issued Secure cookie (`.planning/CONTRACT-CATALOG.md:83`); a broad “locally” directive can cause persistent browser storage to be used without an expiry/revocation policy. Define the exact allowed fields, scope and clear-on-receipt/logout/session-expiry behavior; explicitly exclude prompts, replies and credentials. Test reload recovery and cleanup after receipt/revocation.

### Suggestions
- Add a production build-to-Host asset smoke acceptance jointly owned with 03-03, including cache policy, CSP, base URL and API same-origin behavior.
- Verify the browser test suite actually runs the listed component tests; keep API contract tests separate from UI tests.

### Risk Assessment
**MEDIUM.** Core user states are covered but missing storage semantics can create privacy and recovery bugs, and this plan alone does not close the Host-served UI gap recorded under 03-03.
