# Phases 11–17 source-grounded plan review

Status: **manual source-grounded review; external cross-AI convergence pending**. This checks proposed plans against `docs/PLAN.md`, `docs/PRD.md`, `docs/DECISIONS.md`, `.planning/ROADMAP.md`, and current source boundaries. It does not certify code or satisfy the GSD external reviewer gate. Findings below are current as of 2026-10-03.

## HIGH — revision required before executing the affected plan

| ID | Plan | Required property and observed failure | Example correction |
| --- | --- | --- | --- |
| L-01 | 11-01–04 | **The selected messaging provider must have an implementable authenticated ingress and idempotent outbound contract.** `11-01` proposes Telegram but its automated Go check cannot validate the provider API, credential custody, Hermes seam, or account-link decision; `11-02` then assumes a verified event envelope. | Make `11-01` produce a pinned provider/Hermes qualification fixture or explicit `UNSUPPORTED`, with a proof of sender and retry semantics, and bind `11-02` to that output. |
| L-02 | 12-02 | **The effect must run at the selected node and recheck OS permission locally.** `12-02` modifies a Swift node and Go broker but verifies only `swift test`; the Host dispatch and lost-ACK path are untested. The action also allows switching to a Hermes skill although the file list and Swift test are fixed to a native adapter. | Freeze adapter choice at `12-01`; add Host-to-node integration/receipt verification and branch-specific files/checks. |
| L-03 | 13-02–03 | **A coding run cannot alter the canonical checkout before a distinct approved apply.** Plans promise a disposable sandbox and atomic apply but `13-02` verifies only `./internal/host`, despite Swift executor files, and `13-03` has no Swift or web build check. More critically, the plan does not specify the apply transaction when a patch applies partially or an approval ACK is lost. | Define where apply executes, staging/atomicity and rollback or uncertain state; verify sandbox escape, cancellation and interrupted apply across Host/node/UI. |
| L-04 | 13-04 | **Any platform claimed supported must have an implemented node adapter and live conformance evidence.** The action promises Windows and extra Linux/macOS implementations, while `files_modified` contains only one generic fixture, one Go contract test and evidence; it explicitly postpones adding an adapter. This cannot meet the plan objective. | Either create separate gated platform plans with owned adapter files/toolchains/live checks or narrow this plan and roadmap claims to conformance of already implemented adapters. |
| L-05 | 14-01–04 | **Automation state must be durably integrated with existing Space/Run persistence and effect dispatch.** Four plans introduce `internal/automation` records and a web route but none names the store schema/migration, current run integration, or exact Host execution insertion point. A duplicate tick may be deduped in an isolated ledger yet still cause duplicate external effects. | Bind occurrence/lease/child records to `internal/store` and canonical Space commands; identify one dispatch/approval hook and write crash/replay tests across it. |
| L-06 | 15-01–04 | **Paid release must cover every advertised topology and release chain.** FR-74 and D-041 require combined, separated, managed, and hybrid semantics, but plans only freeze a support matrix and test one selected self-hosted profile. `15-02` tests the Go setup path, not the one-command shell installer, signed manifest or fresh-machine artifact install; `15-04` does not enumerate cross-topology evidence. | Separate artifact/installer proof from a per-topology supported/unsupported matrix; require clean-machine install, signature failure, update/rollback and restore on each claimed profile. |
| L-07 | 16-01–04 | **Managed customer access requires account authentication and scoped control-plane API before provisioning or billing.** `docs/PLAN.md` explicitly lists account authentication. `16-01` decides a principal in prose, while `16-02/03` implement provisioning and billing with no owned authentication/session/tenant-scoping files or negative auth tests. | Add an auth and recovery contract plus executable API/tenant-scoping implementation and isolation tests before exposing provisioned Spaces. |
| L-08 | 17-03–04 | **Shared membership must be approved and enforced at every data serialization and effect path.** `17-03` is docs-only but its `go test` cannot fail on an incomplete threat model or missing owner approval. `17-04` lists only `internal/space/membership.go`, one Host HTTP file and web UI: there is no store migration, policy/context projection, transport/client compatibility or export/restore ownership in file ownership. Thus member filtering can be bypassed by existing endpoints. | Make the owner decision a blocking checkpoint with reviewable role matrix; split implementation into storage/migration, projection, effect policy and client compatibility slices, each with forbidden-data tests. |
| L-09 | 17-01–02 | **An independent implementer must be able to compile and pass conformance without private product internals.** A `sdk/README.md` plus example directory is not an SDK contract; `17-02` runs only Go tests in the private repo. There is no public package boundary, publishing proof, or out-of-tree implementation check. | Specify SDK language/package/API and produce an independent fixture consumer in a clean checkout/container without proprietary imports. |

## Positive coverage and constraints

The plan set does map ROADMAP requirement IDs to phase plans, and within each phase the declared waves form a linear acyclic sequence. It preserves Host-owned Space authority, default deny, approval before consequential effect, idempotent receipts, and truthful uncertain outcomes in intent. These strengths do not resolve the gaps above. External provider/platform documentation and live devices remain separate qualification gates; no live system or code was executed by this review.
