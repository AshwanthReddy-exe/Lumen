# Phases 03–10 source-grounded handoff review

This is a read-only plan audit against the current Go Host, canonical product documents and shared planning contracts on 2026-10-03. It is not an external cross-AI review and does not certify implementation. **HIGH** means a basic executor cannot reach the stated phase checkpoint without making a material design choice or missing a requirement. **MEDIUM** means execution may work but the named check cannot establish the claimed result. Fixes are examples; the invariant in each finding is binding.

## HIGH

1. **03-03 Task 1 — browser access path is not frozen.** The current Host exposes an authenticated Unix control socket (`internal/host/service.go`, `internal/control/server.go`); there is no browser HTTP/TLS listener. `03-03` names `conversation_http.go` and `cmd/lumen-host/main.go`, but asks the executor to “freeze” session issuance, revocation and remote TLS topology while coding. The catalog defers the topology to a `03-03-EVIDENCE.md` file that is absent from this plan's `files_modified`. **Required property:** specify one concrete listener/proxy, trust boundary, owner-authorized session issuance/revocation path, TLS deployment profile and tests before treating the web task as routine. The plan must own all affected files. Example: make this a prior contract/checkpoint task and then implement its recorded choice.

2. **04-04 Task 1 — E8 does not measure accepted-memory usefulness.** The plan uses the public LoTTE Technology search split and qrels, while `docs/PLAN.md` E8 calls for independently authored questions with expected *source memory records*. LoTTE can benchmark a retrieval algorithm, but its qrels do not identify Lumen accepted-memory revisions or demonstrate that scope, correction and task relevance improve later answers. No frozen sample size or numeric usefulness target appears in `04-04` despite the catalog requiring both. **Required property:** E8 must measure authorized accepted-record selection with independent questions and expected Lumen record IDs, a preregistered metric/denominator, and zero unauthorized projections. LoTTE may remain a separate public retrieval baseline.

3. **05-01 Task 2 — unavailable hardware is silently interpreted as client failure.** The action says “If any gate fails or hardware unavailable, record Kotlin Android plus responsive phone-web fallback.” `docs/DECISIONS.md` D-056 selects fallback when the shared client fails the bounded physical gate; `.planning/CLIENT-BRANCHES.md` explicitly defines a third `blocked` state. **Required property:** absence of a named physical Android *or* iPhone yields `BLOCKED`, never a passed fallback decision. A tested failed criterion may select fallback, with its own physical support matrix.

4. **05-04 Tasks 1–2 and 06-03 Task 2 — selected phone branch still has nonexistent fixed paths and a Host-only verification command.** Both frontmatter and `<files>` name `apps/phone/src/...` even though the fallback branch uses `apps/android-host` and responsive `apps/web`; task text says to rewrite the plan during execution. Their `<automated>` checks run Go Host tests only. **Required property:** after 05-01, the committed plans must name only the selected client files and runnable selected-client test/build command before a basic executor starts; no client task is done on a Host-only check. `CLIENT-BRANCHES.md` provides the two alternatives.

5. **06-01 Task 2 — exact approval does not own the shared dispatch enforcement point.** The action invokes `internal/host/execution.go`, and `.planning/CONTRACT-CATALOG.md` says all dispatch callers must pass its durable acceptance path. The task's `<files>` and frontmatter list only `internal/host/approval.go`, its tests and `internal/space/attention.go`; no later Phase 06 task owns `internal/host/execution.go`. A helper can be bypassed by existing `execution.go` callers. **Required property:** the plan must own and test the existing dispatch path, with one atomic grant/approval consumption point for all callers, before claiming FR-31.

6. **07-02 Task 1 — Host is asked to validate a node-local grant it cannot read.** The action states the broker “validates Host and node-local grants” before send. `07-01` places bookmark/root and OS permission inside Mac node state, and `docs/ARCHITECTURE.md` keeps local permission at the node boundary. **Required property:** Host validates only its grant, approval, manifest and target; the node revalidates its local grant and current OS permission immediately before effect and returns a signed denied receipt if either fails. The task and proof must reflect this two-point validation.

7. **07-02 Task 1 — promised Go/Swift signature fixture parity lacks a Swift check.** The action requires RFC 8785 canonical JSON and Go/Swift parity, but `<verify>` runs only `go test ./internal/space ./internal/host`; `07-01` Swift tests precede creation of `invocation-v1.json`, and `07-03` Swift tests need not consume it. **Required property:** one runnable post-fixture cross-language test must fail on changed bytes, digest, key, target or version. Without it, signed cross-node execution may fail or diverge only on physical integration.

8. **08-01 Task 1 — unsupported wake can pass a phase whose exit requires qualified local wake.** The action says to implement tap-to-talk and mark wake `UNSUPPORTED` if no engine qualifies. The Phase 08 roadmap goal and success criterion require physical Android E6 wake at its threshold or supported conditions narrowed; tap-to-talk alone does not meet that result. **Required property:** either leave Phase 08 `BLOCKED/UNSUPPORTED` for wake and continue the independent speech slice with truthful support claims, or obtain owner-approved roadmap/requirement change before treating tap-to-talk as Phase 08 completion.

9. **10-04 Task 2 — Host epoch check is introduced after node/client identity designs are already fixed.** The task requires every enrolled node to pin replacement Host epoch/key and reject old commands. Phase 05's signed envelope includes Host epoch, but `05-04` client tasks and `07-01/07-03` Mac node tasks do not own the persistent accepted-epoch update/rollback-denial ceremony and tests. Phase 10 lists only Go files for epoch fencing. **Required property:** restore/migration checkpoint includes a compatible, tested client and Mac node epoch-acceptance protocol, files and physical old-Host rejection evidence; a Host-only test cannot prove the old Host cannot dispatch to paired nodes.

## MEDIUM

1. **03-05 Task 1 — automated journey does not distinguish live provider success.** The Go contract test can pass with a fake; the action separately requires a real provider answer, Host/runtime restart and browser reattach. **Required property:** phase exit must key off a structured live evidence row with actual version, redacted IDs and `PASS`, not merely the automated test result. Existing text allows `BLOCKED/UNSUPPORTED` rows while the `<done>` criterion does not require a passing live journey.

2. **06-04 Tasks 1–2 — pinned Hermes reply support can remain unsupported while phase completion language remains broad.** The catalog correctly says missing documented reply support disables the route and prevents completion of FR-81. The plan's first `<done>` only says that a certified operation can be enabled, and the second permits an unsupported evidence row. **Required property:** Phase 06 exit explicitly fails for unimplemented clarification delivery and exact action approval if the pinned runtime cannot support the chosen request/reply route; a disabled UI is a truthful status, not fulfillment.

3. **08-02 Task 2 — barge-in is measured but no concrete callback/stream contract establishes it.** The action mentions local synthesis, echo management and immediate stop, yet does not state whether recognition remains active during playback, what event interrupts synthesis, or how callbacks from the old capture generation are discarded. FR-72 requires barge-in. **Required property:** a deterministic test must start playback, inject speech/barge-in, assert playback stops within the preregistered bound and only one recognized utterance enters the Host path.

4. **09-01 Task 1 — real integrated journey can be marked done with `BLOCKED` physical evidence.** The plan's `<done>` accepts either real journey evidence or `BLOCKED`; the Phase 09 roadmap criterion says the real answer, memory correction, approval and target receipt complete in one Space. **Required property:** automated simulation may pass its own lane, but Phase 09 checkpoint remains blocked until the real integrated lane passes on named hardware/provider.

5. **10-01 Task 1 — release trust anchor remains a publication-time choice for a basic executor.** D-054 accepts digest-pinned GitHub Release artifacts, and this plan asks to freeze tag, asset URL, bootstrap checksum and signing key fingerprint before publication. A one-command user cannot manually verify a bootstrap checksum inside that same command. **Required property:** specify the exact first trust anchor and user-facing one-command form (including how the downloaded bootstrap is authenticated), then test fresh install for every claimed OS/arch. Record release-specific values at publish time rather than embedding mutable guesses in the plan.

6. **10-05 Task 2 — seven-day soak has no preregistered acceptance numbers.** The task says to preset p95, availability, memory/storage and recovery thresholds, but neither the plan nor referenced contract specifies them; a basic executor would choose release criteria. **Required property:** owner-approved numerical thresholds, sampling cadence, allowed maintenance window and gap handling are recorded before the clock starts; `soak_test.go` is only a rehearsal.

## Cross-phase checkpoint rule

For every HIGH finding, revise the affected PLAN.md and rerun GSD structure/goal checks before Phase 03 onward is handed to a basic implementation model. Physical evidence, provider credentials, pinned runtime capabilities and owner thresholds are pre-flight gates, never inferred from a successful build or fake test. The shared contracts should be copied into the task action where necessary so the executor sees the exact binding decision at the point of work. Independent security review remains required for auth, protocol, persistence, migration and node execution.
